# Product archive visibility and reviewed restoration

Migration 064 adds permanent visibility intents and reviewed restore receipts. It enrolls no existing archived products, changes no existing product, and sends no Magento request. Normal native synchronization still refuses retired products. A separate visibility lane handles only future deliberate archive/restore intents.

The archive transaction locks the product and its full-product lifecycle, captures both prior records, retires the local product, and invokes `queueArchivedVisibility(client, {productId, actorUserId, mutationContext, previousProduct, previousLifecycle})`. The additive archive response is `visibilityIntent: {status: 'queued'|'blocked'|'not_applicable', intentId, reasonCode}`. Repeated unchanged archives reuse the prior intent. An archive with no confirmed remote product ID keeps a blocked receipt; it never guesses an identity or creates a Magento product.

Any unfinished photo delivery (pending, running, uncertain or blocked) prevents a new archive and restore with PRODUCT_MEDIA_RECONCILIATION_REQUIRED. The archive transaction rolls back product/lifecycle/native-generation changes before commit. Restore preview reports a conflict; sealed apply rechecks it. Even zero-step media jobs are not cancelled speculatively. A predecessor media job
terminally superseded by a proved recount successor is historical evidence, not
an unfinished obligation; the successor job continues to block archive/restore
until it succeeds. Migration 065 can reject started native-input changes earlier
with PHOTO_MEDIA_RECONCILIATION_REQUIRED; the whole transaction still rolls back. Existing archived unfinished media requires an Administrator handoff because ordinary media reconciliation requires an active product and its pinned native generation; no receipt or dispatch marker is reset.

`startProductLifecycle(envConfig, logger, options)` starts one independent five-second lane and returns an asynchronous `stop()`. Its owned pool has at most three connections, one operation runs at a time, and each pass examines at most two intents. Fair rotation keeps an intent waiting for native delivery from starving later hides. Stop drains the active operation before closing the owned pool. Startup never scans archived history to create work.

Visibility work holds the existing public-identity and origin/SKU advisory lanes, but no business transaction or row lock across HTTP. Before dispatch it verifies current local state, captured fingerprint, immutable public SKU, installation/origin, confirmed Magento ID, original archive/restore actor's current archive capability, and the configured delivery actor's publish capability. An exact fresh GET must return the expected remote ID. The only business request is one status-only PUT to the configured origin's exact encoded immutable SKU endpoint. Legacy public articles such as `KL3/...` remain unchanged. Redirects and automatic retries are forbidden.

An old automatic native job can be superseded for a deliberate archive only when it has the exact product, public identity, origin and SKU, an allowed pre-dispatch state, and **zero** `magento_sync_steps` records. Any manual job, verified step, dispatched step, or uncertain job stays intact and blocks visibility work. The cancellation and its audit use the same authorized local transaction. The native queue remains retired rather than becoming an alternate delivery path.

A dispatch marker commits before the PUT. An exact GET after dispatch must confirm the intended status before `verified_at` is recorded. A timeout, partial failure, photo proof change or inconclusive readback remains dispatched and is never resent. Pre-dispatch failures remain blocked. Local status distinguishes archived, queued, blocked, dispatched and verified; only a verified hide exposes `hiddenAt`.

## Reviewed restoration

Restore uses existing `products.view` and `products.archive` permissions, active sessions and CSRF. There are no new role grants. The preview accepts 1–100 exact SKUs, folds case for equality lookup, deduplicates aliases, and preserves the authoritative public article. It selects the current public lineage and rejects corrected ancestors, newer revisions, active successors, test deletions, unresolved delivery, stale archive snapshots, independent exclusions and unknown historical holds. Archived rows without captured prior lifecycle evidence produce a conflict. Old export exclusions are not silently cleared.

`POST /api/products/restore/preview` accepts `{skus}` and returns `reviewNonce`, `reviewHash`, normalized `skus`, counts and per-item found/skipped/conflict evidence. `POST /api/products/restore/apply` requires those exact values plus `confirmRestoreAndSync:true`. Apply rechecks every product, fingerprint, lineage, installation and actor permission in its own transaction. The actor/review hash identifies one immutable batch; repeating the exact reviewed command resumes that batch, including after a lost response. A new preview nonce permits a new deliberate attempt after a previous per-item error.

Local restore changes only active/archive status, the prior exclusion flag, archive attribution and the captured permissible lifecycle route. Price, answers, names, full SKU, public SKU and metadata remain intact. Normal automatic delivery records the new desired generation. Existing remote products use ordinary guarded UPDATE; a missing product can use ordinary CREATE only if captured provenance proves an unexposed ordinary save, with no confirmed/exported/correction/job history. Restore is not a bypass of ordinary eligibility or missing-ID reconciliation.

The inverse visibility intent exists only when a verified hide captured its actual prior status. It waits for succeeded, acknowledged native delivery of the same product/identity/origin and exact current desired generation. Prior hidden status remains hidden. Prior enabled status additionally requires the photo owner's current explicit nonempty gallery proof, a fresh verification of original bytes/order/roles, and unchanged local gallery proof immediately before dispatch and acknowledgement. No captured prior status means visibility is preserved; no receipt can imply enabling.

`GET /api/products/restore/batches/:batchId` returns each item as restored, queued, synced or error. `confirmedAt` exists only for exact current-generation native acknowledgement and, when required, verified visibility restoration. A later desired generation invalidates that batch's current delivery claim. Per-item error receipts and successful restore audit records are permanent. `GET /api/products/:productId/lifecycle` reads local lifecycle and visibility receipts without Magento calls.

## Read-only reconciliation

`POST /api/products/visibility/inspect` with `{intentId}` performs a fresh read-only GET and returns expected/observed Magento IDs, status, target status and a review hash. `POST /api/products/visibility/reconcile` requires `{intentId, reviewHash, confirmVerifiedResult:true}`. It reads again, checks the exact review and all local/permission/generation/photo guards, and can acknowledge only an already-observed exact result of a blocked or dispatched intent. It never sends or retries a Magento write, rebinds a remote ID, or resets a dispatch marker. A blocked hide with no prior status capture retains no inverse enabling authority.

## Integration and verification

Mount `product-lifecycle.routes` behind the application's existing authentication, active-user and CSRF middleware. Start/stop the separate runtime with server lifecycle. The product service owns the archive hook. The photo module owns `signProductVisibilityRequest`, `assertCanEnableVisibility` and `verifyCurrentPhotoSet`; absence fails closed for enabling. `ProductRestoreBatch` is a new modal component; root product register integration owns its open state and navigation guards. Its optional callbacks are `onClose`, `onRestored(receipt)`, `onDirtyChange(boolean)` and `onBusyChange(boolean)`. Uncertain apply responses retain the exact reviewed command and block close/navigation until explicit same-batch recovery. Polls are nonoverlapping and continue after a failed GET; stale principal responses are discarded.

Focused checks cover backend fixture and HTTP boundaries, rendered dialogs and
PostgreSQL transactions, including a terminal predecessor and its current
successor obligation. A checkpoint test inserts an archived product before 064, compares all existing product/lifecycle/native-request/job/audit evidence after the migration, and proves every new visibility/restore ledger is empty. The PostgreSQL fixture uses a uniquely owned `_test` database on the canonical disposable test server, then drops only that exact database. Magento transport is mocked throughout. No test creates live work or contacts the configured real Magento installation. These fixture checks are not acceptance measurements against the real store.
