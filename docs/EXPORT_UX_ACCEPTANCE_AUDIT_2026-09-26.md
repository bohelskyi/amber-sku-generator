# Ручний UX-аудит експорту — 26.09.2026

## Висновок

Основний шлях працює: перевірка товарів → виправлення назви → явна повторна перевірка зі збереженим контекстом → збережена перевірка → створення CSV → окреме підтвердження → історія. Це перевірено через реальний інтерфейс localhost у вбудованому браузері.

Повне UX-приймання поки не рекомендоване. Новому менеджеру заважають обмежений шлях створення умовного правила, зайвий екран після перезавантаження приватного експорту та технічна мова у звичайному сценарії. Втрати даних, неправильного CSV або аварійного завершення застосунку під час цього аудиту не підтверджено. Це не є висновком про всі бізнес-інваріанти чи всі ролі.

Код застосунку не змінювався. Цей документ — результат аудиту, не реалізація рекомендацій.

## Середовище й метод

- Реальний застосунок `http://localhost`, корисна локальна копія БД, відновлена з production; браузер Codex In-app Browser.
- Поточний користувач: Богдан Я. Богельський; у UI користувачів показана роль Administrator. Інші облікові записи не використовувалися для входу.
- Перевірка через видимий UI, DOM/accessibility, знімки екрана та доступні повідомлення консолі. Компоненти, серверний код і БД не використовувалися для визначення очікуваних дій оператора.
- Розміри: 1920×1080, 1440×1000, 390×844. Тимчасові розміри наприкінці скинуто.
- Спроба browser zoom через Ctrl+plus не змінила `innerWidth=1440`, `devicePixelRatio=1`. Справжні 200% **не перевірені**; вузький viewport не підміняє цю перевірку.
- Доступні console error/warn записи під час вибіркових перевірок були порожніми. Окремого журналу HTTP-запитів/HAR інструмент не надав, тому відсутність усіх failed network requests не доведена.
- UI переходив через проміжні loading-стани; результати оцінювалися після завершення завантаження. Тимчасові «Значення №… — назву не підтверджено» при завантаженні характеристик потім замінилися назвами; це не записано як постійна несправність.

## 1. Виправити перед завершенням редизайну

### A01 — Немає зрозумілого переходу від постійного SEO-тексту до нового умовного правила

- **Тип / рівень:** UX bug / **major**. Заявлений операторський сценарій не завершено; це не доводить відсутність можливості у внутрішньому рушії.
- **Маршрут:** `/admin/export-templates/85504d3e-0904-491e-aa0d-e00599ce6692`, таблиця Браслети.
- **Кроки:** відкрити Основний / `meta_title` → розкрити «Як формується значення» → оглянути «Розширені правила цієї колонки».
- **Факт:** звичайний список має лише «Постійне значення» та «Значення характеристики». Немає видимого переходу до тексту з характеристиками чи «Коли / Інакше». Розширений екран відкриває поточний literal і його тип. Водночас уже наявна умова в `name` редагується нормальною формою.
- **Чому заважає:** менеджер може підтримувати готовий складний приклад, але не бачить способу побудувати аналогічне нове SEO-правило. Потрібне знання походження правила чи стороння допомога.
- **Рекомендація:** однаковий видимий вибір «Текст», «Характеристика», «Текст із характеристиками», «За умовами»; зрозумілий перехід між видами зі збереженням/оглядом поточного значення та явним fallback. Це рекомендація до наступної задачі, не зміна в цьому аудиті.
- **Доказ:** скриншот редактора SEO на 1920, де видно два варіанти, і текстові знімки звичайного/розширеного UI. Console error/warn не було; HTTP-трасування недоступне.

### A02 — Reload приватного експорту завершується проміжним майже порожнім екраном

- **Тип / рівень:** UX bug / **major**.
- **Маршрут:** `/exports/sessions/7f0c4985-edd4-4c0f-85dc-efa6f0f5f172`.
- **Кроки:** зберегти перевірку → reload; повторити reload після створення і підтвердження файла.
- **Факт:** залогінений оператор бачить навігацію, «Створити свій експорт», «Відкрити відомий історичний знімок» та кнопку **«Відкрити експорт із посилання через мій обліковий запис»**. Назва й стан потрібного експорту з’являються тільки після цієї кнопки.
- **Чому заважає:** звичайне повернення до роботи виглядає як втрата експорту; сильна сусідня дія створення нового може відволікти від продовження наявного.
- **Рекомендація:** після встановлення актуального користувача виконати звичайне авторизоване read-only відкриття permalink із loading/access-denied станами. Зберегти серверну перевірку членства й fencing; не відновлювати чужі приватні дані з пам’яті браузера.
- **Доказ:** скриншот порожнього проміжного екрана на 1920; повторено для prepared і stored. Помилки консолі не зафіксовані.

### A03 — Основний сценарій вимагає розуміння внутрішньої термінології

- **Тип / рівень:** UX bug / **major** за заданою моделлю нового менеджера.
- **Маршрути:** `/exports/new/template`, незавершена session workspace, `/exports/history/product/*`.
- **Кроки:** «Експорт за опублікованим шаблоном» → створити приватний експорт → оглянути пояснення; у stored result натиснути «Завершити експорт».
- **Факт:** у звичайному режимі є «Вибраний адміністратором кандидат», «Явно вказана опублікована версія», «створення знімка встановлює експозицію товарів», «Автоматичної заміни іншим шаблоном чи legacy немає». Підтвердження пояснює «ревізії цін із цього знімка».
- **Чому заважає:** наслідки важливі, але оператор мусить перекладати терміни рушія перед звичайною дією.
- **Рекомендація:** «Рекомендований шаблон» / «Обрати версію»; коротко пояснити фактичний вплив на товари та чергу, окремо — що це не імпорт у Magento. Деталі експозиції, ревізій і fallback винести в технічний розділ. Не приховувати й не змінювати бізнес-наслідки.
- **Доказ:** текст UI створення та скриншот підтвердження на 390. Помилок консолі не було.

## 2. Сильні покращення для UX-5

### A04 — Загальна кількість проблем не пояснює порожню поточну категорію

- **Тип / рівень:** UX bug / **moderate**.
- **Маршрут:** `/exports`.
- **Кроки:** перевірити 87 нових → залишити Картини → обрати «Потребують уваги».
- **Факт:** «20 товарів потребують уваги», але таблиця порожня: «За цими фільтрами рядків немає». Вкладки не мають кількостей проблем. Натискання загальної кількості правильно переводить у Сувеніри.
- **Чому заважає:** неочевидно, що фільтр обмежено категорією; оператор може сприйняти результат як несправність.
- **Рекомендація:** кількість проблем на вкладках і порожній стан «У Картинах проблем немає; перейти до …». Загальну дію назвати «Показати проблемні товари».
- **Доказ:** скриншот 1440 з порожньою таблицею та загальним числом; console без помилок.

### A05 — Перехід «Відкрити товар» не веде до сфокусованої роботи з проблемою

- **Тип / рівень:** UX bug / **moderate**.
- **Маршрут:** `/exports` → `/?exportSku=SV2314003`.
- **Кроки:** problem cell → «Відкрити товар» → ще раз «Відкрити товар із експорту» → лише декодувати → Back.
- **Факт:** спочатку відкривається загальна сторінка товарів із другою кнопкою. Після декодування без редагування ця кнопка блокується з «Спочатку завершіть або скасуйте поточні зміни товару». Поруч із результатом немає сфокусованої дії повернення до конкретної перевірки. Back зберіг фільтри, але позначив review застарілим навіть без зміни.
- **Чому заважає:** зайвий крок і повідомлення про неіснуючі для оператора зміни. Загальна дія «Переоблікувати» не пояснює, як усунути саме Magento-проблему.
- **Рекомендація:** явний контекст «Відкрито з перевірки експорту», доступна дія повернення; розрізняти перегляд, локальне редагування й успішне збереження. Зберегти захист уже відкритої незбереженої роботи. Для виправлення назви пряма форма в review вже є й працює.
- **Доказ:** текстові знімки handoff/decode/повернення. Немає підтвердженої серверної помилки.

### A06 — У проблемній клітинці причина й основна дія слабші за службовий стан

- **Тип / рівень:** UX bug / **moderate**.
- **Маршрут:** `/exports`, Сувеніри, `name` SV2314003.
- **Кроки:** відкрити клітинку відсутньої назви.
- **Факт:** `Не обчислено` повторюється двічі, потім «Потрібно вказати назву». «Заповнити назву», «Відкрити товар», «Копіювати SKU», «Закрити значення» виглядають подібними текстовими діями.
- **Чому заважає:** оператор спершу читає симптом обчислення й шукає серед рівнозначних дій ту, що виправляє проблему.
- **Рекомендація:** людський заголовок поля, причина першою, помітна основна кнопка виправлення; допоміжні дії другорядні. Не дублювати стан.
- **Доказ:** скриншот діалогу 1440. Помилок консолі не було.

### A07 — Нова копія починається з «історичної структури» й окремого дозволу колонок

- **Тип / рівень:** UX bug / **moderate**.
- **Маршрут:** `/admin/export-templates/system` → нова копія → створена чернетка.
- **Кроки:** «Створити редаговану копію» → назва → зберегти.
- **Факт:** щойно створений шаблон показує «Історична структура колонок. Зміна доступна лише для збереженої чернетки» й «Дозволити додавання й видалення колонок». Після кнопки ревізія стала 2 і з’явилася «+ Колонка».
- **Чому заважає:** новий об’єкт описано як історичний, хоча менеджер щойно попросив редаговану копію. Потрібен ще один неочевидний крок.
- **Рекомендація:** пояснити режим людською мовою і показати доступну дію біля місця додавання колонок. Для нового копіювання розглянути простий вибір режиму без припущення, що оператор знає контракт структури. Семантичну зміну такого режиму погоджувати окремо.
- **Доказ:** текстові знімки ревізій 1/2; помилок консолі не було.

- **Маршрут:** `/exports/history`.
- **Кроки:** створити та підтвердити навчальний експорт → відкрити історію.
- **Факт:** заголовок нового запису просто «Товари», автор «користувач №1». У My exports цей самий користувач має ім’я, а робота — назву «UX-аудит 26.09 — один браслет». Відкриття історії переходить у stored result; назви робочої області й видимого повернення до неї там немає.
- **Чому заважає:** кілька однотипних експортів доводиться відрізняти за датою, шаблоном і SKU; числовий автор мало допомагає команді.
- **Рекомендація:** додати ім’я автора та назву/посилання на наявну дозволену session, коли такі дані авторитетно відомі. Зберегти єдину identity історії; для старих записів не вигадувати власника чи session, для null автора показувати «Автор невідомий».
- **Доказ:** скриншоти history 1920 і 390, My exports 390. Помилок консолі не було.

### A09 — Над таблицею забагато повторів і пояснень

- **Тип / рівень:** UX bug / **moderate**.
- **Маршрути:** `/exports`, `/exports/sessions/:id`.
- **Кроки:** відкрити звичайний preview або підготовлену робочу область на 1440×1000.
- **Факт:** послідовність загальних заголовків, локальної навігації, профілю, часу, діапазону, фільтрів і двох пояснень займає значну частину екрана. У першому preview таблиця починалася майже біля нижнього краю. Профіль та діапазон повторюються між header і review/result.
- **Чому заважає:** головний робочий матеріал відсувається; читання й виправлення партії потребують зайвого вертикального руху.
- **Рекомендація:** компактний workspace header, короткий стан і одна наступна дія; пояснення про CSV/діагностичні значення зробити доступними за запитом. Не змінювати семантику чи модель таблиці.
- **Доказ:** скриншоти preview 1440, stored/share 1440 та history 1920; переповнення ширини сторінки не виявлено.

### A10 — Успішне виправлення ще вимагає ручного переходу до нової перевірки

- **Тип / рівень:** UX improvement / **moderate**; поточна carry-over поведінка **пройшла** приймання цього сценарію.
- **Маршрут:** `/exports`.
- **Кроки:** виправити назву одного проблемного товару у вбудованій формі.
- **Факт:** зрозуміле stale-повідомлення і фокус на «Оновити перевірку» працюють; потрібне ще одне натискання.
- **Рекомендація:** окремо розглянути автоматичне отримання **нового авторитетного read-only preview** після підтвердженої сервером мутації, зі збереженням фільтрів і явним індикатором перевірки. Умови безпеки описані нижче. У цьому аудиті нічого не автоматизовано.
- **Доказ:** скриншот stale 1440 і текстові результати 67→68 готових, 20→19 проблемних; console без помилок.

### A11 — Порожні стани й підказки недостатньо відрізняють відсутність даних від фільтра

- **Тип / рівень:** UX bug / **moderate**.
- **Маршрути:** `/exports/shared`, `/exports/invitations`, `/exports/prices`.
- **Кроки:** відкрити порожні Shared/Invitations; прочитати поточну цінову чергу з 0 рядків.
- **Факт:** запрошення говорять «У цьому списку поки немає експортів». Shared не пояснює, як тут з’являється спільна робота. Порожня цінова черга все одно показує фільтри, порожню таблицю, pagination 0/0 та «За цими фільтрами рядків немає», а корисне «Немає змін цін для експорту» стоїть нижче.
- **Чому заважає:** користувач може шукати неправильний фільтр або не розуміти, чи треба щось створити.
- **Рекомендація:** специфічні порожні стани: «Нових запрошень немає», «Тут з’являться експорти, до яких ви приєднаєтеся», «Усі зміни цін уже опрацьовано / черга порожня» з доречною однією дією оновлення. Не пропонувати створення порожнього експорту.
- **Доказ:** текстові знімки трьох сторінок; помилок консолі не було.

## 4. Майбутня робота після редизайну

Це **future feature**, а не поточні дефекти:

- Magento schema sync: читання наборів атрибутів, кодів та варіантів із Magento; зіставлення з локальними характеристиками й перевірка сумісності до імпорту.
- Валідація під цільовий магазин і огляд змін схеми. Створення атрибутів/варіантів — окрема явна дія й окремий інженерний обсяг.

## Carry-over stale preview — докладний результат

Початково: 87 товарів, 67 готових, 20 потребували уваги. Вибрано **Сувеніри**, SKU-пошук **`SV23`**, **Потребують уваги**, **Основний**. Відкрито проблему `name` товару SV2314003, введено погоджені тестові UA/EN назви й збережено.

UI показав саме:

> Дані товару змінено. Попередній перегляд застарів.
>
> Оновіть перевірку, щоб продовжити роботу з актуальними проблемами.

Фокус перейшов на **Оновити перевірку**. Старий рядок не був виданий за виправлений актуальний результат. Після явного recheck: **68 готових, 19 проблемних**, виправлений SKU зник із attention-вибірки, збереглися категорія, SKU-пошук, readiness і Основний. Фокус опинився в першому актуальному рядку. Відкрито наступну проблему `name` у **SV23150003**; дія **Заповнити назву** була доступна. Другий товар не змінювали.

Це ручне підтвердження основного continuity-сценарію. Окремі зміни ширини колонок і багатосторінкова пагінація в цьому прогоні не перевірялися.

Автоматичний recheck може прибрати механічне натискання після успішного виправлення. Безпечний варіант — новий серверний read-only запит із актуальними principal/session/range/template, явним loading і збереженням лише display context. Якщо він не вдався — лишити stale-стан і ручну дію повторення. Це не повинно локально виправляти клітинку, робити старі діагнози актуальними, зберігати нову підготовку, створювати/підтверджувати файл або змінювати identity незавершеної початкової операції. Для невизначеного результату чи перерваної генерації original-operation retry має залишатися початковим. Така рекомендація потребує окремої реалізації й тестування, її не виконано тут.

## Візуальні докази та обмеження

Скриншоти отримано й показано безпосередньо в розмові: реєстр; новий експорт; порожній attention у Картинах; problem-cell; stale після збереження; Share 1440; history 1920; додавання характеристики 1920; SEO inspector 1920; permalink gate 1920; stored workspace 390; Share 390; confirmation 390; history 390; My exports 390; template registry 390; conditional rule dialog 390; exact-recipient review 390; stored-value dialog 390.

Окремих PNG-файлів у репозиторії немає: доступний браузерний інструмент повернув зображення в розмову без шляхів до файлів. Посилання на неіснуючі картинки не створювалися. Значущі спостереження без окремого скриншота мають текстове UI-відтворення вище.

На оглянутих мобільних списках/діалогах не виявлено page-level horizontal overflow; великі таблиці прокручуються всередині контейнера. Високі редактори мають внутрішній scroll і доступний footer дій. Повного WCAG-аудиту, всіх keyboard-переходів, screen reader і zoom 200% не виконано.

Не було code fixes, stage, commit, push чи запуску destructive integration suite під час цього аудиту. Зміни застосунку, які вже були в робочому дереві до аудиту, збережено. Єдиний новий файловий артефакт цього аудиту — цей звіт.

## Десять змін із найбільшим ефектом для навчання менеджера

1. Дати однаковий зрозумілий шлях створення тексту з характеристиками та умовного правила для будь-якої придатної колонки.
2. Відкривати авторизований session permalink після reload без проміжної кнопки та без послаблення контролю доступу.
3. Замінити «кандидат», «експозиція», «legacy», «ревізії зі знімка» на пояснення дій із товарами, файлами й чергою; технічне залишити в деталях.
4. Показувати кількості проблем по категоріях і явно пояснювати область дії attention-фільтра.
5. Повернути таблиці більшу частину робочого екрана: компактний header, менше повторів, одна наступна дія.
6. Зробити перехід до товару й назад контекстним; не повідомляти про незбережені зміни після простого перегляду.
7. У problem-cell показувати причину й головну кнопку виправлення першими.
8. Прибрати неочевидний «історичний» бар’єр додавання колонок у щойно створеній редагованій копії.
9. Додати до історії відомі людські імена й зв’язок із наявною робочою областю, зберігши спільну identity історії.
10. Окремо реалізувати й перевірити автоматичний новий авторитетний read-only recheck після успішного виправлення, зберігаючи контекст і початкову identity retry.
