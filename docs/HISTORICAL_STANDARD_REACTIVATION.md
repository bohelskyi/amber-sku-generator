# Reviewed historical reactivation through standard delivery

Migration 068 adds a separate intent protocol, `standard-rest-v1`. Applied migrations 066 and 067, old atomic intents, old receipts and ordinary restore-proof requirements remain unchanged. Startup does not enroll historical products or change participation, identity, payload, photos or remote data.

The new protocol reviews current facts. It never reconstructs unknown prior visibility, exclusion, archive-hide acknowledgement or delivery history. A current archived leaf product with an immutable public identity, an authoritative positive Manager price, no corrected ancestry, no independent business exclusion, no test deletion, no unresolved media or delivery work, an authorized actual Administrator and a current approved binding can be reviewed.

For an exact observed counterpart, the review selects UPDATE and pins its exact public SKU and remote entity ID. Its current status and visibility are distinct reviewed fields; normal UPDATE preserves both. For an absent counterpart, the review proposes CREATE under the same public SKU. Confirmation must include that article in a separate explicit `selectedCreateSkus` subset. Normal CREATE remains disabled with status 2. Visibility comes from the reviewed published contract and is not inferred from status 2.

The normal Magento product save route is an upsert. This workflow makes no atomic CREATE-only or UPDATE-only remote guarantee. Fresh observations are compared before enqueue and first dispatch, identities are checked during every readback, and drift stops the operation for another review. A race after the last GET is subject to the supported Magento save semantics. No custom `/V1/amber/...` capability or transport is required for new standard intents.

## Durable sequence

1. Read-only preview releases database transaction locks before remote GET observations. The signed five-minute review binds the actual initiating Administrator, full normalized selection, authoritative product/lifecycle fingerprint, immutable identity, current binding, request generation, remote observation, operation mode and exact normal delivery-plan hash.
2. Explicit confirmation re-observes and revalidates, then records one immutable batch and intent per selected product under the access, lifecycle, publication, public-identity, SKU and product fences. A stable client UUID identifies the batch. Recovery of a committed original request works after preview expiry; changed payload under that UUID conflicts. The local product remains archived.
3. The worker delegates to `magento_sync_jobs` enqueue and APPLY. The existing normal writer, persisted `magento_sync_steps`, GET readback verification, plan integrity and publication/actor checks govern delivery. No second HTTP writer exists in this protocol.
4. After the exact original job succeeds, its immutable acknowledged remote ID and acknowledgement timestamp are recorded. One authorized transaction activates local participation, preserves all other product facts and records the new decision in lifecycle evidence and audit. `deliveryVerifiedAt` and `localActivatedAt` describe these separate events. `hiddenVerifiedAt` stays null for this protocol; no old hide proof is fabricated.
5. An uncertain or partially dispatched job is inspected through existing GET-only recovery. The worker never resends a sticky dispatch. It can record a freshly observed result through the existing reconciliation transaction. Any remaining unsent operation requires the normal explicit reviewed continuation; it is not silently retried by historical polling.

## API contract

The existing `/api/products/historical-reactivation` route defaults to the new standard service. All endpoints require the actual immutable built-in Administrator plus `products.view`, `products.archive`, `history.view`, `export_templates.manage` and `export_templates.publish`; ordinary application CSRF middleware continues to protect mutations.

- `POST /preview {skus}` returns format `historical-reactivation-standard-v1`, protocol `standard-rest-v1`, signed nonce/hash/token/expiry, original normalized `skus`, counts and one item per article. An eligible item includes `deliveryMode`, `requiresExplicitCreate`, `remoteProductId` (null for absence), `targetStatus`, `targetVisibility`, current price, local fingerprint, binding metadata and the sealed normal plan hash.
- `POST /confirm {skus,selectedSkus,selectedCreateSkus,reviewNonce,reviewHash,reviewToken,reviewExpiresAt,idempotencyKey,confirmCurrentFactsAndStandardDelivery:true}` confirms only the exact reviewed eligible subset. `selectedCreateSkus` must equal the selected CREATE articles. The client retains the original UUID and exact original payload for uncertain confirmation; GET by UUID is the recovery path.
- `GET /batches/:batchId` is local read-only receipt lookup. A 404 does not establish that an uncertain confirmation never committed. Old atomic batch UUIDs return their original contract through the old service.
- `GET /intents/:intentId/inspection` exposes the receipt plus `canReconcile`, `canContinue`, `canCancel`, and the ordinary job's `recoveryReview`/`recoveryReviewHash` when relevant. Old atomic intent IDs delegate to the unchanged atomic inspector.
- `POST /reconcile {intentId,review,reviewHash,reason}` performs the normal fresh GET-only local reconciliation and returns an updated raw standard item. It does not dispatch HTTP mutations. Old atomic input/IDs retain their old reconciliation contract.
- `POST /cancel {intentId,confirmNoDispatchCancellation:true}` is an explicit local cancellation. It is permitted only before any dispatch/verification step and before an uncertain or succeeded job. It preserves the old signed review and audit, discovers the original job even if its enqueue reply was lost, and supersedes only that zero-step standard job. The cancellation then permits a fresh review. No old ordinary manual job or started receipt receives this exception.

Receipts include `state` (`queued`, `delivering`, `blocked`, `cancelled`, `completed`), `deliveryMode`, `targetStatus`, `targetVisibility`, `nativeJobId`, `confirmedRemoteProductId`, `deliveryVerifiedAt`, `localActivatedAt`, `nativeConfirmedAt`, `cancelledAt` and `reasonCode`. `nativeConfirmedAt` describes the reviewed normal job acknowledgement; the ordinary automatic outbox may separately confirm the generation created by the local participation change.

Pre-acceptance stale/selection/confirmation failures keep the existing closed codes. New precise blockers include `HISTORICAL_REMOTE_OBSERVATION_CHANGED`, `HISTORICAL_ATOMIC_INTENT_EXISTS`, `HISTORICAL_STANDARD_REVIEW_REQUIRED`, `HISTORICAL_ORIGINAL_ACTOR_REQUIRED` and `HISTORICAL_DELIVERY_RECONCILIATION_REQUIRED`. A blocked untouched intent can be cancelled explicitly and reviewed again. A started intent must use reconciliation instead.

## Verification and rollout

The disposable PostgreSQL fixture uses only canonical `127.0.0.1:55432`, a uniquely marked database ending `_test`, the original four-database inventory and verified cleanup. All Magento observations and supported product-save calls are fixture mocks; global external fetch is forbidden. It proves UPDATE and explicit CREATE, identity/status/visibility preservation, changed observations, stale prices, competing job denial, concurrent UUID recovery, lost HTTP and enqueue replies, GET-only restart reconciliation, zero-step cancellation, lineage rejection, permanent receipts and no startup enrollment. The old atomic fixture is run against 068 to retain its separate contract.

The code and migration require root's reviewed integration, current capability/config projection and corresponding UI contract before deployment. This task does not apply the user's historical article list, publish global bindings, create live products, change production permissions, or install store code.
